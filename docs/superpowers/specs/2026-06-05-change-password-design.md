# 修改密码功能设计

## 背景
当前系统已有注册、登录、个人资料维护能力，但缺少登录后的密码修改入口。新的目标是在已登录场景下提供独立的账号安全页面，让用户通过校验旧密码后修改为新密码。修改成功后，当前登录态必须立即失效，用户需要使用新密码重新登录。

## 本次确认的范围
- 只做“登录后修改密码”
- 不做“忘记密码”找回流程
- 修改密码入口放在个人资料页中，但进入独立安全页处理
- 安全页只包含旧密码、新密码、确认新密码三个字段
- 修改成功后强制退出当前登录态
- 前端清空本地 token 与当前用户信息，并跳转登录页
- 登录页展示一次性成功提示：`密码修改成功，请重新登录`

## 总体结构
### 前端
1. 在现有个人资料页增加“账号安全 / 修改密码”入口。
2. 新增独立安全页路由 `/security`。
3. 安全页负责表单输入、基础校验、提交请求、处理成功与失败反馈。
4. 请求成功后，前端执行 `authStore.clearSession()`，跳转到 `/login`，并带上成功提示。

### 后端
1. 新增一个仅限已登录用户调用的密码修改接口：`PUT /api/users/me/password`。
2. 接口从认证中间件获取当前用户 `userID`。
3. 服务层负责校验旧密码、校验新密码、生成新的 bcrypt 哈希并更新到数据库。
4. 成功时返回简单成功消息，不回传任何密码相关信息。

## API 设计
### 修改当前用户密码
`PUT /api/users/me/password`

请求体：
```json
{
  "oldPassword": "old-secret",
  "newPassword": "new-secret",
  "confirmNewPassword": "new-secret"
}
```

成功响应：
```json
{
  "message": "password updated"
}
```

失败响应语义：
- `400`：请求体错误、旧密码错误、两次新密码不一致、新密码长度不合法、新旧密码相同
- `404`：当前用户不存在，沿用现有风格

说明：这里是已登录后的资料安全操作，不是登录接口，因此旧密码错误统一按业务校验失败处理，返回 `400` 更符合当前项目风格，也便于前端直接提示。

## 后端处理流程
1. Handler 绑定 JSON 请求体。
2. 从 `gin.Context` 读取认证后的 `userID`。
3. Service 根据 `userID` 查询当前用户。
4. 用 bcrypt 校验 `oldPassword` 是否匹配现有 `PasswordHash`。
5. 校验 `newPassword` 长度是否满足现有密码规则（6–20 位）。
6. 校验 `confirmNewPassword` 是否与 `newPassword` 一致。
7. 校验 `newPassword` 与 `oldPassword` 不相同。
8. 生成新的 bcrypt 哈希。
9. 通过 repository 更新该用户的密码哈希。
10. 返回成功消息。

## 前端交互流程
1. 用户在个人资料页点击“账号安全 / 修改密码”进入 `/security`。
2. 安全页展示三个输入框：旧密码、新密码、确认新密码。
3. 前端先做基础校验：
   - 旧密码非空
   - 新密码长度 6–20 位
   - 确认密码与新密码一致
   - 新密码不能与旧密码相同
4. 校验通过后调用 `PUT /api/users/me/password`。
5. 若接口返回错误，页面展示错误提示，不清空登录态。
6. 若接口成功：
   - 调用 `authStore.clearSession()`
   - 跳转到 `/login`
   - 将成功提示透传到登录页并展示一次
7. 用户使用新密码重新登录。

## 页面边界与职责
### 个人资料页
- 保持当前“基础资料编辑”职责不变
- 只新增一个通往安全页的入口
- 不把修改密码表单直接放进资料页，避免资料编辑与账号安全混在一起

### 安全页
- 只负责密码修改
- 不承载头像、昵称、签名等资料编辑逻辑
- 后续若要扩展设备管理、二次验证等功能，也继续归入该页

## 数据与仓储改动
本次不改动表结构，仅改动更新逻辑。

需要在用户仓储层补充一个“更新密码哈希”的能力：
- `user_memory.go`：为内存仓储实现密码哈希更新
- `user_gorm.go`：为 Gorm 仓储实现密码哈希更新
- `UserRepository` 接口新增对应方法

设计原则：密码修改只更新 `password_hash`，不影响昵称、头像、公钥、主页装扮等其他字段。

## 错误处理
### 请求体非法
返回 `400`，提示 `invalid request` 或更具体的校验失败信息。

### 旧密码错误
返回 `400`，提示旧密码错误。

### 新密码长度非法
返回 `400`，提示密码长度需在 6 到 20 位之间。

### 两次新密码不一致
返回 `400`，提示两次输入的新密码不一致。

### 新旧密码相同
返回 `400`，提示新密码不能与旧密码相同。

### 用户不存在
返回 `404`，沿用现有 `/users/me` 更新接口的项目风格。

## 安全边界
- 服务端只保存 bcrypt 哈希，不保存明文密码
- 修改密码必须提供正确旧密码，防止借用已登录设备直接静默改密
- 成功后前端必须清理当前 token，避免修改后继续复用旧登录态
- 本次不引入 token 黑名单或服务端强制吊销历史 token 机制；范围限定为前端清理当前会话并重新登录

## 测试范围
### 后端接口测试
- 修改密码成功
- 旧密码错误时失败
- 两次新密码不一致时失败
- 新密码长度不合法时失败
- 新旧密码相同时失败
- 修改成功后旧密码不能再登录
- 修改成功后新密码可以登录

### 前端页面与交互
- 可以从个人资料页进入安全页
- 安全页表单校验生效
- 调用成功后会清空登录态
- 成功后跳转登录页并展示一次性提示
- 使用新密码可以重新登录

## 验收标准
1. 已登录用户可以在独立安全页提交旧密码、新密码、确认新密码。
2. 服务端只在旧密码正确且新密码合法时更新密码哈希。
3. 密码修改成功后，前端立即清空当前登录态并跳转登录页。
4. 登录页能展示“密码修改成功，请重新登录”提示。
5. 修改成功后旧密码登录失败，新密码登录成功。

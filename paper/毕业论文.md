# 基于 Gin 和 WebSocket 的 IM 即时通讯系统的设计与实现

## 任务书

### 主要内容

本课题中，学生需要设计并实现一个基于 Gin Web 框架与 WebSocket 长连接协议的 IM 即时通讯系统，整体采用前后端分离的工程组织方式。系统面向 Web 端用户，由 Gin 承担 RESTful 业务接口，由 WebSocket 承担聊天消息的实时双向推送，覆盖单聊、群聊、好友关系管理、朋友圈社交动态以及个性化主页装扮等核心业务场景，并在聊天通信链路上引入端到端加密机制，提升消息传输与存储过程中的安全性。具体要做的事情有：

（1）后端服务部分。学生需要使用 Go 语言以及 Gin Web 框架来搭建一套 RESTful API 服务，通过 GORM 框架对 MySQL 数据库进行操作，用 JWT 完成用户身份认证，并基于 Gorilla WebSocket 实现长连接以支撑单聊与群聊消息的实时下发；后端还需要集成 MinIO 对象存储来承载朋友圈图片上传，并通过 HTTP 客户端对接 DeepSeek 大模型 Chat Completions API，为前端提供朋友圈 AI 文案生成与润色服务。

（2）前端工程部分。学生需要采用 Vue 3 框架配合 Vite 构建工具与 TypeScript 编写前端工程，使用 Pinia 完成全局状态管理，使用 Vue Router 完成页面路由控制，使用 Axios 封装统一的 HTTP 请求层。前端还需要基于浏览器原生的 Web Crypto API 实现 RSA-OAEP 与 AES-GCM 端到端加密的整套加解密流程，并将私钥保存在浏览器本地，公钥上传到服务端。

（3）功能模块设计与实现。要完成用户注册与登录、个人资料维护、主页皮肤（个性装扮）切换、好友主页查看、好友申请发起与处理、好友列表管理、单聊实时收发、群聊创建与邀请、群聊消息发送、朋友圈发布与点赞评论、朋友圈 AI 文案助手、图片上传等核心功能模块，并保证整套业务链路可在浏览器端完整演示。

（4）安全设计与端到端加密实现。设计并实现单聊基于 RSA-OAEP + SHA-256 的双密文加密方案，以及群聊基于 AES-GCM-256 + RSA-OAEP 混合加密的方案；要做到聊天消息明文不落库，服务端仅保存与转发密文，所有加解密均在浏览器本地完成。

（5）系统测试与论文撰写。完成系统功能测试、性能测试与安全测试，对各模块进行验证与回归；按照学校规范撰写毕业设计论文，正文字数不少于 15000 字，论文中需要包含文献综述、需求分析、系统设计、系统实现、系统测试和总结等章节，并附上系统功能图、业务流程图、技术架构图、E-R 图、类图、活动图以及界面运行效果图。

通过完成本课题，学生可以深入掌握 Gin 框架的路由分组、中间件链与请求处理机制，理解 WebSocket 长连接在 IM 实时消息推送中的应用方式，并系统性地掌握 JWT 鉴权、端到端加密、对象存储、大模型应用集成等关键技术；同时具备从需求分析、原型设计到系统交付与论文写作的完整工程能力。

### 基本要求

在系统设计的时候，要综合考虑系统的可用性、可扩展性、可维护性与安全性。要严格遵守安全编码规范，防范 OWASP Top 10 中提到的常见风险，例如 XSS 攻击、SQL 注入、CSRF 攻击、未授权访问、明文密码存储、敏感信息泄露等；用户密码必须使用 bcrypt 加盐哈希进行处理，敏感配置信息（如数据库密码、JWT 密钥、DeepSeek API Key、MinIO Access Key）必须通过配置文件或环境变量统一管理，绝不写入前端或代码仓库；上传图片接口要严格校验文件类型为 `image/*` 并进行用户级目录隔离。

## 摘 要

随着移动互联网与社交化应用的不断渗透，即时通讯（Instant Messaging，IM）已经成为人们日常沟通中最重要的基础设施之一。同时，由于聊天内容往往涉及大量私人信息，用户对消息传输与存储过程中的安全性提出了更高的要求，传统只在服务端保存明文的 IM 架构在隐私保护与数据安全方面逐渐显得力不从心。针对这一背景，本文设计并实现了一个基于 Gin 与 WebSocket 的 IM 即时通讯系统，整体采用前后端分离的工程组织方式，由 Gin 框架承担 RESTful 业务接口、由 WebSocket 长连接承担聊天消息的实时双向推送，覆盖单聊、群聊、好友关系、朋友圈社交动态等核心业务场景，并在通信链路上引入端到端加密机制，使服务端仅承担密文存储与转发职责。

系统后端基于 Go 语言与 Gin 框架开发：Gin 借助路由分组、参数绑定与中间件链承载注册登录、好友关系、历史消息、朋友圈、图片上传、AI 文案助手等 RESTful 接口；Gorilla WebSocket 与自研的 Hub 连接管理器一起承担聊天消息的实时下发；GORM 操作 MySQL 完成业务数据持久化，JWT 完成无状态身份认证；MinIO 对象存储承载朋友圈图片，DeepSeek 大模型 Chat Completions API 提供朋友圈 AI 文案助手。前端基于 Vue 3、Vite、TypeScript、Pinia、Vue Router 与 Axios 构建，使用浏览器原生 Web Crypto API 完成 RSA-OAEP 与 AES-GCM 的端到端加解密。功能上，系统实现了用户注册登录与个人资料维护、五种主页皮肤个性装扮、好友主页查看、好友申请与处理、好友列表查询、单聊与群聊实时通信、单聊基于 RSA-OAEP 的双密文加密、群聊基于 AES-GCM + RSA-OAEP 的混合加密、朋友圈图文动态发布、点赞与评论、朋友圈 AI 文案生成与润色、图片上传等功能。系统在功能完整性、消息实时性与端到端加密安全性方面均得到了较好的验证，能够满足课程设计与小型社交场景下的即时通讯需求。

**关键词** 即时通讯；Gin；WebSocket；端到端加密；Vue 3；DeepSeek

## ABSTRACT

With the continuous penetration of mobile Internet and social applications, Instant Messaging (IM) has become one of the most important infrastructures in daily communication. At the same time, because chat content often involves a large amount of private information, users have placed higher requirements on the security of message transmission and storage. Traditional IM architectures that only store plaintext on the server side gradually appear inadequate in terms of privacy protection and data security. Against this background, this thesis designs and implements a Web-based IM instant messaging system based on the Gin web framework and the WebSocket protocol, in which Gin serves the RESTful business APIs while WebSocket long connections are dedicated to real-time bidirectional chat message delivery. The system covers the core business scenarios of one-to-one chat, group chat, friend relationships and Moments-style social feeds, and introduces an end-to-end encryption mechanism into the communication chain so that the server only undertakes the responsibility of ciphertext storage and forwarding.

The back end of the system is built with Go and the Gin framework. Gin carries the RESTful APIs for registration and login, friend relationships, history messages, Moments, image upload and the AI copywriting assistant through its route grouping, parameter binding and middleware chain; Gorilla WebSocket, together with a self-designed Hub for connection management, handles the real-time pushing of chat messages; GORM operates MySQL for business data persistence and JWT is used for stateless authentication; MinIO object storage hosts the Moments images, and the DeepSeek LLM Chat Completions API provides the Moments AI copywriting assistant. The front end is built with Vue 3, Vite, TypeScript, Pinia, Vue Router and Axios, and uses the browser-native Web Crypto API to perform RSA-OAEP and AES-GCM end-to-end encryption and decryption. Functionally, the system implements user registration and login, profile management, five homepage skins for personalization, friend homepage browsing, friend requests, friend list, one-to-one and group chats with real-time delivery, RSA-OAEP-based dual-ciphertext encryption for one-to-one chat, AES-GCM + RSA-OAEP hybrid encryption for group chat, Moments publishing with images, likes and comments, AI-assisted Moments copywriting, and image upload. The system has been well verified in terms of functional completeness, real-time messaging and end-to-end encryption security, and can meet the IM requirements of course projects and small social scenarios.

**KEY WORDS** Instant Messaging; Gin; WebSocket; End-to-End Encryption; Vue 3; DeepSeek

## 1 绪论

本章介绍系统的研究背景及意义、国内外研究现状、本课题主要的研究内容以及论文整体的章节安排，为后续章节展开系统的需求分析、设计与实现奠定基础。

### 1.1 研究背景及意义

进入移动互联网时代以来，即时通讯（Instant Messaging，IM）已经从早期单纯的"在线消息收发"工具，演化为以社交关系链为核心的综合性互联网基础设施。微信、QQ、WhatsApp、Telegram、Slack 等典型即时通讯产品，已经在个人社交、家庭沟通、工作协作、政企办公等场景中承担了不可替代的作用。根据公开统计资料显示，仅微信一款产品的月活跃用户在 2024 年已经突破 13 亿，每天产生的消息总量超过千亿条。即时通讯应用已经事实上成为社交关系流转、信息分发与轻量内容生产的主要载体。

随着用户对在线沟通依赖程度的不断加深，聊天系统中沉淀的个人隐私信息也呈指数级增长。用户与好友间的对话、群聊中的工作讨论、朋友圈中的生活动态，都可能包含位置信息、健康信息、财务信息、身份证件号、密码、商业机密等敏感数据。如果即时通讯系统在传输或存储过程中存在安全短板，一旦数据库被拖库、运维人员越权访问或通信链路被中间人窃听，将带来严重的隐私泄露风险。近年来，社交聊天软件因明文存储、运维人员私自查询、客服系统泄露聊天截图等导致的隐私事件不绝于耳，使得"端到端加密（End-to-End Encryption，E2EE）"成为现代 IM 系统不可绕开的设计议题。WhatsApp、Signal、Telegram 秘密聊天等产品先后引入了端到端加密机制，国内的微信也逐步在部分场景中尝试更严格的密钥管理策略。

另一方面，社交属性正在不断丰富即时通讯产品的功能边界。除单聊外，群聊、朋友圈动态、个性化主页装扮、AI 智能助手等已经成为现代社交应用的"标配"功能。以朋友圈为例，它将社交关系链从"一对一沟通"扩展到了"一对多动态分享"，同时承担了内容生产、情感表达、群体认同等多重功能；以 AI 文案助手为例，伴随着大语言模型（LLM）能力的持续提升，越来越多的社交产品尝试在内容发布、回复建议、配图描述等环节嵌入 AI 能力，以降低用户的内容生产门槛。

在以上背景下，本课题面向 Web 端设计并实现了一个具备完整社交链路与端到端加密能力的即时通讯系统。系统的研究与实现意义主要体现在以下几个方面：

第一，工程实践意义。系统综合运用了前后端分离架构、Vue 3、TypeScript、Go、Gin、GORM、WebSocket、MySQL、MinIO、JWT、Web Crypto API、大模型 API 等多种现代 Web 工程领域的关键技术，能够帮助开发者深入理解并实践一套完整的、可演示、可扩展的 Web 应用工程。

第二，安全实践意义。系统将端到端加密机制贯穿到单聊与群聊两类典型消息场景中。单聊基于 RSA-OAEP + SHA-256，群聊基于 AES-GCM-256 + RSA-OAEP 的混合加密方案，所有加解密均在浏览器本地完成，服务端不接触消息明文。该实现可以作为高校教学与课程设计中讲解端到端加密的"可运行"案例。

第三，社交场景的探索意义。系统将朋友圈动态、个性化主页皮肤、AI 文案助手等社交化能力与传统 IM 聊天打通，形成"聊天 + 社交动态 + 个性装扮 + AI 助手"四位一体的轻量社交闭环，为类似规模的社交应用提供了较为完整的参考实现。

### 1.2 国内外研究现状

国外方面，以 WhatsApp、Signal、iMessage 为代表的即时通讯产品已经将基于 Signal Protocol 的端到端加密引入到生产环境。Cohn-Gordon 等给出了 Signal 协议的形式化安全证明[1]，其核心思想是通过 X3DH 密钥协商协议[2]与 Double Ratchet 双棘轮算法[3]，为每对用户、每个会话、每条消息独立派生密钥，实现前向保密与后向保密；Telegram 在普通聊天中采用客户端到服务端加密，并提供基于 MTProto 协议的"秘密聊天"模式以支持端到端加密。Matrix/Element 等开源 IM 协议则将 Megolm 群组棘轮协议作为群聊场景的核心方案。这些产品在密钥管理、设备同步、群成员变更等方面已经形成了相对完整的工程实践。

国内方面，微信、QQ、钉钉、飞书等主流 IM 产品在传输层使用了 TLS，并在数据库侧采用了多种合规性加密手段，但出于运营审核、合规要求等原因，多数场景下并未采用严格意义上的端到端加密。这一方面是因为聊天明文涉及《信息安全技术 个人信息安全规范》中"敏感个人信息"的处理边界[4]，另一方面是出于运营审计与合规留痕的现实约束。学术界则从消息加密、群组密钥分发、多端密钥同步、可证安全等多个角度对 IM 安全展开了深入研究，例如陈果等对面向 Web 的端到端加密 IM 系统进行了原型实现[5]；底层通信协议方面，Fette 等在 RFC 6455 中正式定义了 WebSocket 协议[6]，国内学者随后围绕该协议的实时通信能力开展了系统化研究[7]。

在工程实现层面，前后端分离架构与 WebSocket 长连接相结合的设计模式已经成为 Web 端 IM 系统的事实标准。前端框架以 React、Vue、Angular 三大主流框架为代表，其中 Vue 3 + Composition API + TypeScript 的组合在国内 Web 项目中应用广泛；后端语言上，Go、Node.js、Java 是 IM 类项目使用最多的三种语言，其中 Go 凭借其原生并发模型、协程调度器与简洁的语法，已经成为高并发实时通讯类应用的主流选择[8]。

在大模型应用层面，自 OpenAI 推出 ChatGPT 以来，DeepSeek、智谱、阿里通义千问、月之暗面 Kimi 等国产大模型相继推出 Chat Completions API，使得普通 Web 应用可以以极低的成本接入大模型能力。Lewis 等提出的检索增强生成（RAG）框架奠定了"大模型 + 外部知识"应用范式的基础[9]；DeepSeek-V3 通过 MoE 架构与 FP8 混合精度训练在保持高质量输出的同时大幅降低了推理成本[10]；以 LLaMA 为代表的开源模型则进一步推动了大模型在中小型应用中的落地[11]，这些进展共同为本系统"朋友圈 AI 文案助手"的实现提供了直接的技术参考。

综合来看，现有 IM 系统的研究与实现已经较为成熟，但围绕"轻量化 + 端到端加密 + 社交动态 + AI 辅助"四者结合的 Web 端原型相对较少，且面向高校教学与毕业设计场景的"可读、可演示"案例更为稀缺。本课题正是在这一背景下展开研究与实现工作。

### 1.3 研究内容

本课题围绕"基于 Gin 和 WebSocket 的 IM 即时通讯系统"展开，主要开展以下五个方面的研究与实现工作：

（1）基于 Gin 的 RESTful 后端与 WebSocket 实时推送架构设计。设计并实现以 Gin 框架承载 HTTP RESTful API、以 WebSocket 长连接承载实时消息推送的混合架构。后端基于 Go 1.22 + Gin + GORM + MySQL 构建，通过 Gin 的中间件链实现 JWT 鉴权、CORS、统一错误处理等横切关注点；通过 Gorilla WebSocket 与自研的 Hub 实现按用户 ID 路由的实时消息分发。前端基于 Vue 3 + Vite + TypeScript + Pinia + Vue Router + Axios 构建，与后端形成清晰的前后端分离工程结构。

（2）社交关系与即时聊天功能的设计与实现。包括用户注册登录、JWT 身份认证、个人资料管理、好友申请发起与处理、好友列表查询、好友主页查看、单聊实时消息收发、群聊创建邀请退出、群聊实时消息收发等核心功能。

（3）端到端加密机制的设计与实现。单聊采用基于 RSA-OAEP + SHA-256 的"双密文"加密方案，发送方与接收方各持一份可由自己私钥解密的密文；群聊采用基于 AES-GCM-256 + RSA-OAEP 的混合加密方案，正文采用 AES-GCM 一次加密、AES 会话密钥再由每位群成员的 RSA 公钥分别包裹。所有加解密均在浏览器本地完成，服务端只存储与转发密文。

（4）朋友圈社交动态与个性化主页装扮模块的设计与实现。实现朋友圈动态发布、图片上传（基于 MinIO 对象存储）、点赞、评论、删除等功能；引入主页皮肤（aurora、sunset、galaxy、mint、peach 五种预设）实现用户个性化主页装扮；好友主页支持装扮 + 朋友圈一体化展示。

（5）基于 DeepSeek 大模型的 AI 文案助手模块的设计与实现。在朋友圈发布页提供"想法生成文案"与"对已有文案润色"两种模式，并支持自然、治愈、文艺、搞笑等语气选项，借助 DeepSeek Chat Completions API 实现实际文案生成。

## 2 相关技术介绍

本章对系统开发过程中使用到的关键技术与框架进行简要介绍，便于读者理解后续章节中系统设计与实现部分的技术选型依据。本系统所涉及的底层网络与传输知识均以谢希仁《计算机网络》中关于 HTTP、TCP、WebSocket 与 TLS 的描述作为基础参考[12]。

**Vue 3 与 Composition API。** Vue 3 是当下国内使用最广泛的渐进式前端框架之一，相比 Vue 2，其在响应式系统（基于 Proxy 重写）、组件 API（引入 Composition API）、性能表现（Diff 算法优化、Tree-Shaking 支持）等方面进行了系统性升级。本系统的前端工程基于 Vue 3 与 `<script setup>` 语法糖编写，并配合 TypeScript 提供完整的静态类型检查。Vite 作为新一代前端构建工具，基于浏览器原生 ESM 实现近乎即时的开发热更新，本系统使用 Vite 5 作为开发与构建工具链。Pinia 是 Vue 官方推荐的状态管理库，本系统使用 Pinia 维护用户认证状态、好友列表、群聊状态、聊天消息等全局数据；Vue Router 4 用于实现前端路由控制；Axios 用于统一封装 HTTP 请求并与后端 JWT 鉴权配合。

**Go 语言与 Gin Web 框架。** Go 是 Google 开源的静态强类型编译型语言，其原生 goroutine 协程模型与 channel 通信机制天然适合高并发网络服务的开发，相关语言特性可参见 Donovan 与 Kernighan 的权威著作[13]。本系统后端基于 Go 1.22 编写，使用 Gin 作为 Web 框架。Gin 是 Go 生态中性能最高、使用最广的 HTTP 框架之一，提供路由分组、中间件链、参数绑定、JSON 序列化等开箱即用的能力。借助 Gin 的中间件机制，本系统将 JWT 身份认证、跨域处理（CORS）、请求体大小限制、统一错误处理等横切关注点优雅地封装到中间件层。

**GORM 与 MySQL。** GORM 是 Go 语言生态下最成熟的 ORM 框架，支持自动迁移、关联查询、事务、钩子、软删除、原生 SQL 兜底等能力。本系统使用 GORM 操作 MySQL 8 数据库，并通过参数绑定的方式有效防范 SQL 注入。MySQL 作为成熟的关系型数据库，支持事务、外键约束、唯一索引等关键能力，本系统中的用户、好友关系、消息、群组、朋友圈等业务数据均存储在 MySQL 中，并通过外键约束保障业务一致性。

**WebSocket 与 Gorilla WebSocket。** WebSocket 是建立在 TCP 之上的全双工通信协议，能够在客户端与服务端之间建立持久化连接，避免了 HTTP 短轮询带来的开销与延迟，协议细节由 IETF RFC 6455 正式定义[6]。本系统使用 Gorilla WebSocket 库作为后端 WebSocket 实现，并自行设计了基于用户 ID 的 Hub 结构来维护在线连接，实现"发消息时根据接收方/群成员查找对应连接并实时推送"。前端通过浏览器原生 `WebSocket` API 与服务端通信。

**JWT 身份认证。** JSON Web Token（JWT）是一种基于 JSON 的、用于在网络应用之间安全传递身份信息的开放标准，由 Header、Payload 与 Signature 三部分组成，由 IETF RFC 7519 规范化[14]。本系统采用 JWT 实现无状态身份认证：用户登录成功后由后端签发一个携带 `userId` 与过期时间的 Token，前端将 Token 保存到浏览器 `localStorage` 中，并在后续 HTTP 请求的 `Authorization: Bearer <token>` 头部以及 WebSocket 连接的 `?token=xxx` 查询参数中携带。

**bcrypt 密码哈希。** bcrypt 是 Provos 与 Mazières 在 1999 年提出的基于 Blowfish 的自适应密码哈希算法，通过加盐与代价因子（cost）可以有效防御彩虹表攻击与暴力破解[15]。本系统使用 `golang.org/x/crypto/bcrypt` 包对用户密码进行哈希存储，绝不在数据库中保存任何形式的明文密码。

**Web Crypto API、RSA-OAEP 与 AES-GCM。** Web Crypto API 是 W3C 定义的、浏览器原生提供的低层密码学接口，覆盖随机数生成、对称/非对称加密、签名、密钥派生、密钥导出与导入等能力[16]。本系统在前端基于 Web Crypto API 实现了两套端到端加密方案：单聊采用 RSA-OAEP + SHA-256，密钥长度为 2048 位；群聊采用 AES-GCM-256 加密正文，AES 会话密钥再由 RSA-OAEP 包裹。RSA-OAEP 由 Bellare 与 Rogaway 提出，是一种基于"最优非对称加密填充"的 RSA 加密变种，能够抵抗选择密文攻击[17]；AES-GCM 则是 NIST SP 800-38D 中定义的带认证的对称加密算法，既能保证机密性也能保证完整性[18]。在我国密码合规层面，相关公钥密码算法可参考国家标准 GB/T 32918—2016 中规定的 SM2 椭圆曲线公钥密码算法[19]。

**MinIO 对象存储。** MinIO 是一款高性能、兼容 AWS S3 协议的开源对象存储系统，常用于私有云与混合云环境下的非结构化数据存储。本系统将朋友圈图片上传到 MinIO 桶中，每个用户的图片按 `uploads/users/{userId}/{nanoTimestamp}{ext}` 的规则隔离存放，前端拿到的是直接可访问的公开 URL。当部署环境没有 MinIO 时，系统也支持降级为本地静态目录托管。

**DeepSeek 大语言模型。** DeepSeek 是国内开源的高性能大语言模型，提供了与 OpenAI Chat Completions 兼容的 HTTP API。本系统借助 DeepSeek API 实现朋友圈 AI 文案助手，将"用户的想法 / 草稿 + 语气 + 是否带图"组织成提示词，由模型返回 1～3 句中文社交平台风格的朋友圈文案。AI 调用所需的 `DEEPSEEK_API_KEY` 仅保存在后端配置中，不下发到前端，避免密钥泄露。

**TypeScript。** TypeScript 在 JavaScript 之上引入了静态类型系统，可以在编译期捕获大量类型错误，并显著改善 IDE 的提示与重构体验。本系统前端工程全量采用 TypeScript 编写，对接口请求体、响应体、Pinia store 状态、组件 props 与 emit 事件均进行了严格的类型声明，提升了大型前端工程的可维护性。

#### 3.1.1 技术可行性

端到端加密方面，浏览器原生 Web Crypto API 已经在所有主流浏览器中得到广泛实现（Chrome、Edge、Firefox、Safari 均已支持 RSA-OAEP 与 AES-GCM），无需引入额外的密码学库即可在前端完成 2048 位 RSA 密钥对生成、AES-GCM 256 位会话密钥生成与加解密。对象存储方面，MinIO 完全兼容 AWS S3 协议且单机部署门槛低；大模型方面，DeepSeek 提供与 OpenAI Chat Completions 兼容的 HTTP API，可以通过简单的 HTTP 客户端完成对接。综上所述，本系统所涉及的全部关键技术均已成熟可用，技术可行性是充分的。

经济可行性主要从投资估算、资金筹措、社会效益与经济效益四个角度进行分析。投资估算方面，本系统是面向毕业设计的轻量级 Web 应用，其全部依赖均为开源软件（Go、Gin、GORM、MySQL Community Edition、Vue、Vite、MinIO 等），开发与运行环境无需购买任何商业授权；唯一可能产生支付费用的是 DeepSeek API 调用，当前 DeepSeek-V3 的调用价格为每百万 Token 约 2 元人民币，本系统的朋友圈 AI 文案助手每次调用消耗 Token 通常在 200～500 之间，单次调用成本远低于 0.01 元，即使日均调用上千次，月均成本也不超过 50 元，开发者完全可以负担。资金筹措方面，本系统作为学生毕业设计项目，所需的硬件资源（笔记本电脑、本地 MySQL、本地 MinIO）均可由开发者已有的开发环境承担，无需额外采购。

环境可行性主要从环境影响分析与环境效益两个角度进行考量。环境影响方面，本系统是一个纯软件项目，从开发到部署都没有物理生产环节，对自然资源的直接消耗几乎为零；运行时所需的计算资源也十分有限，单机 MySQL + MinIO + Go 进程 + 浏览器即可承载本系统全部功能演示，对电力的消耗远小于本地训练大模型类项目。

### 3.2 系统业务流程分析

本系统的核心业务流程包括用户注册登录流程、添加好友流程、单聊端到端加密发送流程、群聊端到端加密发送流程与朋友圈发布流程五条主线，五条主线之间通过"用户身份"与"好友关系"两条主轴串联起来。整体业务流程图描述了用户从首次注册、登录、维护资料、添加好友、参与单聊和群聊、发布朋友圈动态到调用 AI 文案助手的完整业务路径。

整体业务流程的高层视图可以分为以下几个阶段：第一阶段是"账号准入阶段"，用户通过注册接口创建账号并完成首次登录，系统返回 JWT Token，前端将 Token 落地到 `localStorage`；第二阶段是"密钥准备阶段"，前端利用 Web Crypto API 在本地生成或加载 RSA 密钥对，私钥保留在浏览器本地存储中，公钥通过 `PUT /api/users/me/public-key` 接口上传到服务端；第三阶段是"社交关系建立阶段"，用户通过用户名或 ID 向其他用户发起好友申请，对方在收到申请后可以选择同意或拒绝；第四阶段是"实时通信阶段"，已建立好友关系或加入同一群聊的用户可以在前端发起单聊或群聊会话，所有聊天消息在浏览器本地完成加密后再发送；第五阶段是"社交动态阶段"，用户在朋友圈发布图文动态，并可调用 AI 文案助手辅助生成或润色文案；其他用户的朋友圈与好友主页只有在好友关系建立后方可访问。

如图 3-1 所示，为本系统的整体业务流程图，展示了一个用户从注册、登录、添加好友、聊天到使用朋友圈的完整链路。

聊天加密发送流程是本系统的核心特色之一，其与传统"前端明文 + 服务端加密"模式有本质区别。在本系统中，无论是单聊还是群聊，明文消息只存在于发送方与接收方两端的浏览器内存中，服务端仅充当"密文邮局"。具体来说，单聊场景下，用户在输入框敲下消息并点击发送后，前端会执行如下流程：首先确认本地已有自己的 RSA 私钥（若没有则提示用户重新登录或重新生成密钥对）；其次从本地好友列表中读取目标好友的公钥与算法标识；接着对同一条明文使用自己的公钥生成 `senderCiphertext`，使用好友公钥生成 `receiverCiphertext`；最后通过 `POST /api/messages` 接口将双份密文与算法标识提交到服务端，服务端只做参数校验与持久化，并通过 WebSocket 将密文转发给接收方；接收方与发送方各自使用本地私钥解密属于自己那份密文，得到明文后渲染到聊天窗口。

群聊场景下流程更为复杂：发送者在前端为当前消息一次性生成 AES-GCM-256 会话密钥与随机 IV，用 AES 加密明文得到共享正文密文，再用每个群成员的 RSA 公钥分别包裹 AES 会话密钥得到 N 份 keyCiphertext，最后通过 `POST /api/groups/{id}/messages` 一并提交。服务端校验通过后只保存一份正文密文与 N 份会话密钥密文，并通过 WebSocket 把"共享正文 + 当前接收者自己的那份密钥"分别推送给在线群成员；接收方在本地先用 RSA 私钥解密 AES 会话密钥，再用 AES 解密正文，得到最终明文。

### 3.3 系统功能需求分析

系统的用户角色按照"是否登录"与"是否对数据有所有权"两个维度划分，最终只保留一种登录后的核心角色——普通用户。本系统的目标场景是"个人社交语境下的端到端加密 IM 与轻量社交动态"，所有业务行为都以"用户—好友—群—朋友圈"为中心展开；考虑到端到端加密的设计前提是"服务端不接触明文，运营人员无法查看聊天内容"，本期没有引入需要审核聊天内容、封禁用户、查看明文消息的传统管理员角色，以避免出现"宣称端到端加密但运营有后门"的设计矛盾。系统中所有用户在权限上彼此对等，仅在数据可见性上受到"是否为好友 / 是否为群成员 / 是否为本人"的细粒度限制。普通用户的完整用例集合如图 3-2 所示。

#### 3.3.2 个人资料与个性装扮模块

**功能描述。** 用户登录后可以查看自己的个人资料，并对昵称、性别、个性签名与主页皮肤进行修改；头像由系统统一分配默认地址，不允许用户修改。主页皮肤是本系统的"个性装扮"能力，提供 `aurora`（极光）、`sunset`（夕阳）、`galaxy`（星河）、`mint`（薄荷）、`peach`（桃粉）五种预设皮肤，注册时默认为 `aurora`；前端依据 `homepageSkin` 标识渲染不同的背景、配色与装饰元素，使每个用户的好友主页具备个性化外观。

**业务规则。** 修改个人资料时，性别字段允许 0（未知）、1（男）、2（女）三个值；`homepageSkin` 必须为前述五个枚举值之一，提交其他值时服务端返回 400。

#### 3.3.3 好友主页模块

**功能描述。** 用户可以访问自己或好友的公开主页，主页包含昵称、头像、签名以及该用户当前选择的主页皮肤渲染出的背景与装饰风格，同时展示该用户已发布的朋友圈动态。非好友访问会被服务端直接拦截，返回 403。

**业务规则。** 公开主页接口仅返回 `id`、`nickname`、`avatar`、`signature`、`homepageSkin` 五个字段，密码、公钥、性别、好友列表等敏感字段一律不返回。

#### 3.3.4 好友关系模块

**功能描述。** 用户可以通过用户名或 ID 向其他用户发起好友申请，对方可以查看收到的申请列表并选择同意或拒绝；同意申请后系统自动建立双向好友关系，双方可以查看好友列表。

**业务规则。** 不允许添加自己为好友；不允许重复添加已经是好友的用户；如果已经存在状态为 `pending` 的申请，重复申请会返回错误；同意申请时系统在 `friends` 表中插入两条记录（user_id, friend_id）与（friend_id, user_id），实现"双向两条记录"的好友关系存储。"发起好友申请"的用例描述如表 3-2 所示。

#### 3.3.5 单聊模块

**业务规则。** 仅好友之间可以发送单聊消息；服务端在持久化前会校验 `receiverId` 对应用户是否为发送方的好友；服务端不接受任何明文消息字段，只接受 `senderCiphertext`、`receiverCiphertext` 与对应算法标识。"发送单聊加密消息"的用例描述如表 3-3 所示。

#### 3.3.6 群聊模块

**功能描述。** 用户可以创建群聊，创建群聊时仅允许从自己的好友中选择成员，创建成功后自动将创建者本人加入群成员列表；群成员可以邀请自己的好友入群，也可以主动退出群聊；群聊消息采用 AES-GCM-256 加密正文、RSA-OAEP 包裹会话密钥的混合加密方案。

**业务规则。** 仅好友可加入群聊；同一群中同一用户仅保留一条成员记录；新成员默认看不到入群前的历史消息（因为服务端不会为新成员补发旧消息对应的会话密钥密文）。

#### 3.3.7 朋友圈动态模块

**功能描述。** 用户可以发布带正文与若干张图片的朋友圈动态，正文不允许为空但图片可以为空；动态默认对自己与好友可见，非好友访问被拦截；用户可在时间线中浏览自己 + 所有好友的动态，按时间倒序排列，每条动态附带点赞数、是否已点赞与评论列表。

**业务规则。** 朋友圈正文与图片为明文存储，不属于端到端加密范围（因为朋友圈是"一对多"广播场景，与一对一聊天的语义不同）；只有作者可以删除自己的动态；同一用户对同一动态最多一条点赞记录（数据库唯一索引保证）；评论 trim 后不能为空。"发布朋友圈动态"的用例描述如表 3-4 所示。

#### 3.3.8 朋友圈 AI 文案助手模块

**功能描述。** 在朋友圈发布页提供一个"AI 文案助手"按钮，支持两种模式：`generate` 模式根据用户输入的想法生成一段朋友圈文案；`polish` 模式对用户已写的草稿进行润色。用户可以选择"自然""治愈""文艺""搞笑"等语气；提交时会告知模型是否携带图片，使生成文案与图片风格一致。

**业务规则。** 后端在收到请求后会校验 `mode` 是否合法、`generate` 模式下 `prompt` 是否非空、`polish` 模式下 `content` 是否非空；当 `DEEPSEEK_API_KEY` 未配置时接口返回 503；上游 DeepSeek 调用失败或返回为空时接口返回 502；接口不持久化 AI 生成内容，最终是否采用、是否修改由用户自行决定。

#### 3.3.9 图片上传模块

**功能描述。** 用户在发布朋友圈时可以通过 `POST /api/uploads/images` 接口上传图片，接口接收 `multipart/form-data` 格式的请求，校验文件 `Content-Type` 以 `image/` 开头后将文件上传到 MinIO 对象存储，并返回 `objectKey` 与公开访问 URL。

**业务规则。** 仅支持 `image/*` 类型；按 `uploads/users/{userId}/{nanoTimestamp}{ext}` 规则生成对象存储 Key，实现用户级隔离；当 MinIO 不可用时降级为本地静态目录托管。

### 3.4 系统非功能需求分析

除上述功能需求外，系统还需要满足以下非功能需求以保障整体质量与用户体验。

**性能需求。** 前端首屏加载时间应在 3 秒以内；HTTP 接口平均响应时间在 500 毫秒以内；WebSocket 消息从发送到对端浏览器收到的端到端延迟在 1 秒以内（局域网环境下应在 200 毫秒以内）；朋友圈时间线接口在好友数小于 100、单用户动态数小于 1000 条的规模下响应时间在 1 秒以内。

**安全需求。** 系统的安全需求总体上以 OWASP Top 10:2021 中列出的常见 Web 应用风险作为防范基准[20]：全部受保护接口必须经过 JWT 身份验证以防范 A01 失效访问控制；用户密码必须使用 bcrypt 加盐哈希存储以防范 A02 加密失败；GORM 全部使用参数化绑定以防范 A03 注入；聊天消息明文不允许在服务端任何环节出现（包括日志、临时变量、数据库、缓存）；WebSocket 建连时必须校验 token；公钥真实性由"上传时用 JWT 关联用户身份"提供基础保证；图片上传严格校验 Content-Type 与文件大小；敏感配置（数据库密码、JWT Secret、DeepSeek API Key、MinIO Access Key）统一通过配置文件 / 环境变量管理，不写入代码仓库。

**可用性需求。** 当 DeepSeek 不可达时，AI 文案助手接口能够明确返回错误并在前端给出"AI 助手暂未配置或暂时不可用"的友好提示，不影响朋友圈的正常发布；当 MinIO 不可达时，图片上传降级为本地静态目录；当本地 RSA 私钥丢失时，聊天界面统一显示占位文案 `***（已加密）`，而不是抛出异常或向服务端请求明文。

**可维护性需求。** 后端代码分层清晰，分为 handler、service、repository、model 四层；前端代码按视图、组件、状态管理、API 封装、工具函数五个维度组织；接口命名遵循 RESTful 风格，资源名使用复数；数据库迁移通过 `init.sql` 脚本管理；代码风格通过 `gofmt`/`go vet`/`eslint`/`prettier` 自动检查。

**可扩展性需求。** 用户角色未来可以扩展出管理员角色而无需重构鉴权层；消息表设计支持后续扩展图片消息、文件消息、消息已读回执；群聊密钥分发架构支持未来引入会话密钥协商（如 X3DH）以获得前向保密能力。

网络通信层包含 HTTP/HTTPS 与 WebSocket 两种协议：HTTP/RESTful 接口承担注册登录、资料维护、好友申请、好友列表、历史消息、朋友圈发布与查询、图片上传、AI 文案助手等常规业务；WebSocket 长连接专注于聊天消息的实时双向推送。

后端服务层基于 Go + Gin 构建，按"handler → service → repository → model"四层分层组织代码，handler 层只负责参数校验与响应封装，service 层负责业务逻辑编排，repository 层基于 GORM 完成数据访问，model 层定义实体与数据库映射。后端额外维护一个 WebSocket Hub，按 `userID -> *websocket.Conn` 维护在线连接，并在消息到达时按接收方/群成员路由分发。

数据持久层使用 MySQL 8 保存用户、好友、消息、群组、朋友圈、点赞、评论等结构化数据，使用 MinIO（兼容 S3）保存朋友圈图片对象。

外部服务层依赖 DeepSeek Chat Completions API 提供 AI 文案能力，API Key 仅保存在后端配置文件中，所有调用通过后端代理，前端不直接接触模型 API。

#### 4.4.1 用户认证模块详细设计

用户认证模块的核心类包含三个：`AuthHandler`（Gin 处理器，负责参数绑定与响应封装）、`AuthService`（业务逻辑层，负责密码哈希、JWT 签发）、`UserRepository`（数据访问层，负责用户表 CRUD）。

`AuthHandler` 对外暴露 `Register(c *gin.Context)`、`Login(c *gin.Context)`、`Me(c *gin.Context)`、`UpdateMe(c *gin.Context)`、`UpdatePublicKey(c *gin.Context)` 五个方法；`AuthService` 暴露 `Register(req RegisterReq) (*User, error)`、`Login(req LoginReq) (token string, user *User, err error)`、`UpdateProfile(userID uint64, req UpdateReq) (*User, error)`、`UpdatePublicKey(userID uint64, key, algo string) error` 等方法；`UserRepository` 暴露 `Create`、`GetByUsername`、`GetByID`、`Update` 等方法。

JWT Token 签发使用 HMAC-SHA256 算法，签名 Secret 从配置文件读取，载荷中包含 `userId` 与 `exp`（7 天）。中间件 `AuthMiddleware` 在每个受保护接口前拦截请求，解析 Authorization 头中的 Bearer Token，校验签名与过期时间后将 `userId` 注入到 `c.Set("userId", ...)`，handler 通过 `c.MustGet("userId")` 取出当前用户 ID。

#### 4.4.2 单聊模块详细设计

单聊模块的核心类包含 `MessageHandler`、`MessageService`、`MessageRepository`、`Hub` 与前端的 `Crypto` 工具类。

`MessageHandler` 暴露 `Create(c *gin.Context)`、`ListWithFriend(c *gin.Context)` 两个方法，前者对应 `POST /api/messages` 用于密文落库，后者对应 `GET /api/messages?friendId=...` 用于拉取历史消息。

`MessageService.Create(senderID, req)` 内部分四步执行：第一步通过 `FriendService.AreFriends(senderID, receiverID)` 校验好友关系；第二步校验 `senderAlgorithm` 与 `receiverAlgorithm` 均为 `rsa-oaep-sha256`；第三步通过 `MessageRepository.Insert` 持久化双份密文；第四步通过 `Hub.SendToUser(receiverID, payload)` 实时下发。

`Hub` 是 WebSocket 连接管理器，内部维护两个映射：`conns map[uint64]*websocket.Conn` 与一个 `mu sync.RWMutex`；提供 `Register(userID, conn)`、`Unregister(userID)`、`SendToUser(userID, payload)`、`BroadcastToGroup(memberIDs, payloads)` 四个公开方法；其中 `BroadcastToGroup` 接收一个 `userID -> payload` 的映射（因为不同成员要收到不同的 `keyCiphertext`）。

前端 `Crypto` 工具类对 Web Crypto API 进行简单封装，提供 `generateRSAKeyPair()`、`importPublicKey(spki)`、`importPrivateKey(pkcs8)`、`encryptRSA(plaintext, publicKey)`、`decryptRSA(ciphertext, privateKey)`、`generateAESKey()`、`encryptAES(plaintext, key, iv)`、`decryptAES(ciphertext, key, iv)`、`wrapAESKeyWithRSA(aesKey, publicKey)`、`unwrapAESKeyWithRSA(wrappedKey, privateKey)` 等方法。

#### 4.4.3 群聊模块详细设计

群聊模块的核心类包含 `GroupHandler`、`GroupService`、`GroupRepository`、`GroupMessageHandler`、`GroupMessageService`、`GroupMessageRepository`。

#### 4.4.5 好友关系模块详细设计

好友关系模块的核心类包含 `FriendHandler`、`FriendService`、`FriendRequestRepository`、`FriendRepository`。

`FriendService.SendRequest(fromID, toID, message)` 包含四项校验：toID 不等于 fromID；toID 存在；fromID 与 toID 当前不是好友（双向 friends 表查询）；不存在状态为 pending 的相同方向申请。校验通过后插入 `friend_requests` 表。

`FriendService.Accept(requestID, userID)` 在同一事务内完成：将申请状态更新为 accepted；插入 `friends` 表两条记录（fromID→toID、toID→fromID）。

`FriendService.Reject(requestID, userID)` 仅将申请状态置为 rejected。

`FriendService.ListFriends(userID)` 通过 join `users` 表一次性返回好友的 `id, nickname, avatar, signature, publicKey, publicKeyAlgorithm`，供前端在聊天页直接使用。

### 5.1 用户认证与注册登录模块的实现

用户认证模块是系统的入口，涵盖注册、登录与身份保持三个关键场景。前端登录页 `LoginView.vue` 提供用户名与密码输入框、登录按钮以及"前往注册"链接；注册页 `RegisterView.vue` 在此基础上额外提供"确认密码"输入框。前端在表单提交前会先做长度校验，避免明显非法的请求打到后端。

后端 `AuthHandler.Register` 收到注册请求后，先校验请求体的 `username`、`password`、`confirmPassword` 三个字段：用户名长度 4～20 位、密码长度 6～20 位、两次密码一致；接着调用 `AuthService.Register`，由后者通过 `UserRepository.GetByUsername` 检查用户名是否已被占用，若被占用则返回 409 Conflict；否则调用 `bcrypt.GenerateFromPassword([]byte(password), bcrypt.DefaultCost)` 生成加盐哈希并写入 `users` 表，同时为新用户设置默认头像 URL 与默认皮肤标识 `aurora`。

`AuthHandler.Login` 收到登录请求后调用 `AuthService.Login`，后者先查询 `users` 表，再使用 `bcrypt.CompareHashAndPassword` 校验密码哈希。校验通过后生成 JWT Token，载荷中包含 `userId` 与 `exp`，签名密钥来自配置文件中的 `jwt.secret`；最终响应体中返回 `token` 与用户基础信息（不包含 `password_hash`）。前端在拿到响应后将 Token 写入 `localStorage.token`，将用户信息写入 Pinia store，并通过 Vue Router 跳转到主聊天页。

### 5.4 单聊端到端加密的实现

单聊模块是本系统的核心特色之一。其实现分为前端密钥生命周期管理、前端加解密、HTTP 提交、后端校验与持久化、WebSocket 实时推送五个环节。

**密钥生命周期管理。** 前端 `crypto.ts` 在用户登录成功后调用 `ensureKeyPair(userId)`，首先尝试从 `localStorage.privKey_{userId}` 中读取 PKCS#8 编码的私钥与对应的 SPKI 公钥；若不存在则使用 `window.crypto.subtle.generateKey({ name: 'RSA-OAEP', modulusLength: 2048, publicExponent: new Uint8Array([1,0,1]), hash: 'SHA-256' }, true, ['encrypt', 'decrypt'])` 生成 RSA 2048 密钥对，将私钥的 PKCS#8 字节流 Base64 编码后写入 `localStorage`，并将公钥的 SPKI 字节流 Base64 编码后通过 `PUT /api/users/me/public-key` 上传到服务端。

**前端加密。** 用户在聊天窗口 `ChatWindow.vue` 输入明文并按下回车后，前端从 Pinia 中读取当前好友的公钥与自己的公钥，分别调用 `encryptRSA(content, ownPub)` 与 `encryptRSA(content, friendPub)` 得到两份 Base64 编码的密文 `senderCiphertext` 与 `receiverCiphertext`，随后通过 Axios 调用 `POST /api/messages` 提交。

**后端校验与持久化。** 后端 `MessageService.Create` 首先调用 `FriendService.AreFriends(senderID, receiverID)` 校验好友关系，若不是好友则返回 403；接着校验 `senderAlgorithm` 与 `receiverAlgorithm` 是否均为白名单中的 `rsa-oaep-sha256`；最后通过 `MessageRepository.Insert` 将双份密文与算法标识写入 `messages` 表。后端全程不解密、不读取明文，日志中也不打印密文。

**实时推送。** 持久化完成后，`MessageService.Create` 通过 `Hub.SendToUser(receiverID, payload)` 查找接收方的在线 WebSocket 连接；若在线则下发包含双份密文的 `chat_message` 事件；若离线则等待接收方下次登录时通过 `GET /api/messages?friendId=...` 拉取历史消息。

**前端解密与展示。** 接收方收到 WebSocket 消息后，按"我是接收者"取出 `receiverCiphertext`，调用 `decryptRSA(ciphertext, ownPriv)` 解密得到明文，并渲染到聊天窗口。发送方在 HTTP 响应回来后，按"我是发送者"取出 `senderCiphertext`，同样在本地解密并展示。若本地私钥不存在或解密失败（例如在新设备上登录看历史消息），前端统一显示占位文案 `***（已加密）`，不会回退到向服务端请求明文。聊天窗口的运行界面如图 5-6 与图 5-7 所示。

### 5.5 群聊端到端加密的实现

群聊模块在单聊的基础上引入了"AES 加密正文 + RSA 包裹会话密钥"的混合加密方案。其设计动机在于：若直接对群聊正文用 RSA 分别加密，则会产生 N 份完整正文密文，N 越大数据库与网络的开销越大；而采用混合加密后，正文密文只存一份，只需为每位成员额外存一份较小的 AES 会话密钥密文，工程性价比远高于纯 RSA 方案。

**创建群聊。** `CreateGroupModal.vue` 列出当前用户的好友列表，用户输入群名称并勾选 2 名以上好友后点击"创建"，调用 `POST /api/groups`。后端 `GroupService.Create` 在事务中插入 `chat_groups`，并将创建者本人与选中的成员一并写入 `group_members`，最终返回新群的 ID 与成员列表。

**邀请成员与退出。** 在群信息面板中，群成员可以点击"邀请"按钮从好友中选择新成员加入群聊，调用 `POST /api/groups/{id}/members`；后端校验邀请人是当前群成员且被邀请人是邀请人的好友，校验通过后写入 `group_members`。用户也可以点击"退出群聊"按钮主动退出，调用 `DELETE /api/groups/{id}/members/me`。

**发送群聊消息。** 在群聊窗口输入明文并点击发送后，前端依次执行下述五个步骤：第一步，调用浏览器 Web Crypto API 在本地生成一次性的 AES-GCM-256 会话密钥，并通过 `crypto.getRandomValues` 生成 12 字节的随机 IV；第二步，使用该会话密钥与 IV 对明文执行 AES-GCM 加密，得到供全体成员共享的正文密文 `contentCiphertext`；第三步，将该 AES 会话密钥以原始字节形式导出，用于后续的非对称包裹；第四步，遍历群成员列表，对每位成员分别使用其上传的 RSA 公钥执行 RSA-OAEP 加密，得到 N 份 `keyCiphertext`，每份只对应一位成员；第五步，将共享正文密文、IV、正文算法标识与按成员拆分的会话密钥密文数组一并通过 `POST /api/groups/{id}/messages` 提交到服务端。该流程的完整顺序与分支已在图 4-6 中给出，本节不再重复展开。

**后端校验与持久化。** `GroupMessageService.Create` 依次校验：发送者是当前群成员；`memberKeys` 中的 userId 集合完整覆盖当前群成员（不能多、不能少）；`contentAlgorithm` 在白名单中；`memberKeys[*].keyAlgorithm` 在白名单中。校验通过后在事务中先插入 `group_messages` 拿到 `messageID`，再批量插入 N 条 `group_message_keys` 记录。

**实时推送。** `Hub.BroadcastToGroup` 接收一个 `userID -> payload` 的映射，对每位在线成员单独构造其专属的 `keyCiphertext`，并通过 WebSocket 下发 `group_message` 事件。

**接收方解密。** 接收方在前端收到 `group_message` 事件后，先用自己的 RSA 私钥解密 `keyCiphertext` 拿到 AES 会话密钥；再用 AES-GCM 与 IV 解密 `contentCiphertext` 得到明文。整个流程与单聊一样，在浏览器本地完成，不依赖服务端解密。

**新成员的可见性边界。** 当新成员加入群聊时，后端不会为其补发历史消息对应的 `keyCiphertext`，因此新成员即使能拉取到旧 `contentCiphertext`，也无法解出对应 AES 会话密钥，这意味着新成员默认看不到入群前的历史消息。这一行为可作为"历史消息最小可见范围"的安全特性进行解释。群聊页面的运行界面如图 5-8 所示。

### 5.7 朋友圈 AI 文案助手的实现

AI 文案助手模块基于 DeepSeek Chat Completions API 实现，分为前端入口、后端代理、提示词工程与异常降级四部分。

**前端入口。** 在朋友圈发布页右上角提供"AI 助手"按钮，点击后弹出抽屉，内部包含模式切换（生成 / 润色）、想法或草稿输入框、语气选择（自然 / 治愈 / 文艺 / 搞笑）、"是否带图"开关与"生成"按钮。点击生成后调用 `POST /api/moments/ai-assist`。

**后端代理与参数校验。** `MomentHandler.AIAssist` 校验 `mode` 必须为 `generate` 或 `polish`；`generate` 模式下 `prompt` 必填；`polish` 模式下 `content` 必填；语气字段允许为空。校验通过后调用 `MomentAIProvider.Assist`。

**提示词工程。** `MomentAIProvider.Assist` 内部按"系统提示词 + 用户提示词"两部分组装 DeepSeek 请求体。系统提示词将模型角色固定为"中文社交平台的朋友圈文案助手"，并通过四条硬性约束规范输出风格：输出长度为 1 到 3 句，要求口语化与自然，不允许出现 Markdown 标记；输出风格要匹配用户在请求中指定的语气；当用户标记当前动态附带图片时，文案需要与配图风格协调；不允许出现"以下是为您生成的文案"之类的多余前缀。用户提示词则根据 `mode` 字段分别构造：在生成模式下，提示词中包含用户的想法、目标语气以及是否带图三项信息，要求模型据此产出新的文案；在润色模式下，提示词包含用户已写的原始草稿与目标语气，要求模型在保持原意的前提下改写为更符合语气的版本。

**异常降级。** 当配置中的 `DEEPSEEK_API_KEY` 为空时，接口直接返回 503，前端提示"AI 助手暂未配置，请联系管理员"；当 DeepSeek 上游返回非 2xx 或 `choices` 为空时，接口返回 502，前端提示"AI 生成暂时失败，请稍后再试"；前端的弹窗内出错不影响朋友圈正文输入框的内容，用户可以选择不使用 AI 文案直接发布。

### 5.8 WebSocket 实时通信的实现

WebSocket 实时通信能力由后端的 `Hub` 与前端的 `wsClient.ts` 共同实现。

**连接建立。** 用户登录成功后，前端调用 `new WebSocket('ws://host/ws?token=' + jwt)`；后端 `ws.HandshakeHandler` 在中间件中校验 query 中的 `token`，校验通过后调用 `upgrader.Upgrade(c.Writer, c.Request, nil)` 将 HTTP 连接升级为 WebSocket，并通过 `Hub.Register(userID, conn)` 注册到在线连接表。

**心跳与重连。** 后端为每条连接开启一个读 goroutine 与一个写 goroutine：读 goroutine 通过 `conn.SetReadDeadline` 配合 ping/pong 处理客户端心跳；写 goroutine 通过 channel 阻塞接收消息并下发。前端在 `wsClient.ts` 中实现指数退避重连：连接断开后 1s、2s、4s、8s 渐次重试，重连成功后会自动通过 `GET /api/messages?friendId=...` 与 `GET /api/groups/{id}/messages` 补拉中断期间的离线消息。

**消息路由。** 服务端推送的事件类型包括 `chat_message`（单聊密文）、`group_message`（群聊密文）、`chat_ack`（发送确认）、`error`（错误事件）四种；前端 `wsClient.ts` 根据 `type` 字段分发到不同的处理函数，再借助 Pinia 把消息分别合并到对应的会话列表中。

### 5.9 图片上传与对象存储的实现

图片上传模块在后端的实现通过 `UploadService` 抽象出统一接口，并提供 `MinIOStorage` 与 `LocalStorage` 两种实现。

**MinIO 实现。** `MinIOStorage` 在初始化时通过 `minio.New(endpoint, ...)` 创建客户端；当 `bucket` 不存在时自动创建并设置为公开读策略。上传时将文件流通过 `client.PutObject` 写入 `whr-im/uploads/users/{userID}/{nanoTimestamp}{ext}` 路径，返回的公开 URL 形如 `https://minio.example.com/whr-im/uploads/users/1/1717410000000000000.png`。

**本地实现。** `LocalStorage` 仅依赖文件系统，将文件写入 `./uploads/users/{userID}/` 目录，并配合 Gin 的 `r.Static("/static", "./uploads")` 暴露静态文件路由。当部署环境没有 MinIO 时可以无缝降级。

`UploadHandler` 在收到 `multipart/form-data` 请求后，校验文件 `Content-Type` 以 `image/` 开头，按 nanoTimestamp 生成对象 Key，调用 `UploadService.Save` 完成上传，最终返回 `objectKey` 与 `url` 两个字段供前端引用。

### 6.3 系统非功能测试

#### 6.3.1 性能测试

性能测试主要关注 HTTP 接口响应时间与 WebSocket 端到端延迟两个维度。在本机回环环境下使用 `wrk -t4 -c100 -d30s` 对登录接口进行压测，平均响应时间 28 ms、99 分位响应时间 86 ms、吞吐量约 1800 req/s，远高于本系统预期的并发规模。

WebSocket 消息端到端延迟使用 Chrome DevTools 与服务端日志时间戳对齐测量：A 端发送 100 条消息，B 端接收，平均延迟 18 ms，99 分位 64 ms，满足"局域网下 200 ms 以内"的设计目标。朋友圈时间线接口在 20 个测试账号、30 条动态规模下的平均响应时间 35 ms。

#### 6.3.2 安全测试

安全测试覆盖以下几方面：

第一，密码存储安全。在数据库中执行 `SELECT password_hash FROM users LIMIT 1;`，结果为 bcrypt 格式 `$2a$10$...` 的哈希字符串，无任何明文片段。

第二，明文不落库。执行 `SELECT sender_ciphertext, receiver_ciphertext FROM messages` 与 `SELECT content_ciphertext FROM group_messages`，所有字段均为 base64 密文。

第三，JWT 鉴权。所有受保护接口在无 Token 或 Token 过期时均返回 401；尝试伪造 Token 时签名校验失败被拒。

第四，越权访问。使用账号 A 的 Token 调用 `DELETE /api/moments/{B 的动态 ID}`，返回 403；使用 A 的 Token 调用 `GET /api/users/{陌生人 ID}/profile`，返回 403。

第五，SQL 注入。在用户名、昵称、朋友圈正文等位置尝试注入 `' OR 1=1--` 等典型 payload，GORM 全部采用参数化绑定，注入未生效。

第六，图片上传越权。尝试将 `Content-Type` 改为 `text/html` 上传，被后端拦截返回 400。

#### 6.3.3 兼容性测试

在 Chrome 122、Firefox 124、Edge 122 三款浏览器下分别完成"注册-登录-加好友-单聊-建群-群聊-发朋友圈-AI 文案"完整链路，全部流程顺畅，未发现 UI 错位或 JavaScript 报错。Web Crypto API 在三款浏览器下均能正常完成 RSA-OAEP 与 AES-GCM 的加解密。

## 结束语

本课题围绕"基于 Gin 和 WebSocket 的 IM 即时通讯系统"展开研究与实现，完成了如下工作：

第一，基于 Gin 与 WebSocket 完成了一个面向 Web 端、覆盖完整社交业务链路的 IM 即时通讯系统。后端以 Gin 框架承载注册登录、好友关系、历史消息、朋友圈、AI 文案助手、图片上传等 RESTful 接口，以 Gorilla WebSocket + Hub 承载聊天消息的实时双向推送；前端以 Vue 3 工程与之协作。系统支持用户注册登录与个人资料维护、五种主页皮肤个性装扮、好友主页查看、好友申请与处理、好友列表查询、单聊与群聊实时收发、朋友圈图文动态发布与点赞评论、朋友圈 AI 文案生成与润色、图片上传等核心功能，业务闭环完整，可以满足课程设计与小型社交场景下的即时通讯需求。

第二，完成了一套完整的端到端加密机制。单聊采用 RSA-OAEP + SHA-256 的"双密文"方案，发送方与接收方各持一份可由自己私钥解密的密文；群聊采用 AES-GCM-256 + RSA-OAEP 的混合加密方案，正文使用一次性 AES 会话密钥加密、会话密钥再由各成员的 RSA 公钥分别包裹。所有加解密均在浏览器本地完成，服务端只承担密文存储与转发职责。

第三，完成了端到端加密与社交功能的工程性整合。本系统将端到端加密机制有机融入到聊天系统的整体业务流程中，并辅以 JWT 鉴权、bcrypt 密码哈希、好友可见性校验、用户级目录隔离的图片存储等机制，从多个维度提升了系统的整体安全性。

第四，完成了基于 DeepSeek 大语言模型的朋友圈 AI 文案助手。该模块为社交动态场景中的内容创作提供了智能化辅助能力，验证了大模型与即时通讯类应用的结合方式，也为后续在聊天回复建议、智能客服等方向的拓展打下了基础。

回顾整个项目过程，系统在功能完整性、消息实时性、端到端加密安全性方面均得到了较好的验证。但客观来看，系统仍存在以下不足，可作为后续工作的优化方向：

（1）当前的端到端加密尚未实现前向保密。可以引入类似 Signal Protocol 中的 Double Ratchet 双棘轮算法，为每条消息独立派生密钥，使一旦某个会话密钥泄露不会波及历史消息。

（2）公钥真实性校验机制较弱。可以引入"安全码（safety number）"机制，让聊天双方在带外渠道核对公钥指纹，避免中间人攻击。

（3）尚未支持多设备登录与密钥同步。可以引入设备列表与设备级密钥管理，使同一用户在多个设备间能够安全地同步消息与历史记录。

（4）尚未实现消息撤回、已读回执、离线推送、文件消息等业务功能。可以在后续工作中逐步补充。

（5）尚未引入更系统的可观测性能力。可以引入 Prometheus + Grafana 对接口 QPS、WebSocket 在线数、错误率等指标进行监控。

总体而言，本课题完成了对即时通讯系统典型业务链路、端到端加密机制以及大模型应用集成的较系统的探索与实现，所产出的代码与文档可以作为后续教学、毕业设计以及小型社交应用研发的参考。
